# Архитектурные драйверы AdScale

## 1. Бизнес-цели

За три месяца подключить крупного DSP-партнёра, сохранить текущих клиентов и непрерывную работу. Система должна выдерживать не менее 18 000 запросов/с, общий P95 не более 100 мс и отдельное требование партнёра: ответ не более 80 мс.

Через год нужны 50 000 запросов/с, доступность 99,9%, микросервисы, обмен событиями, горизонтальное масштабирование, несколько регионов и подключение нескольких рекламных площадок.

В кейсе также упоминается двукратный рост за год. Для проектирования принимаем явно указанную итоговую цель 50 000 запросов/с, поскольку она строже. Двукратный рост от текущих 15 000 запросов/с дал бы только 30 000.

## 2. Функциональные требования

| № п.п. | Требование после интеграции                                                                                     |
| ------ | --------------------------------------------------------------------------------------------------------------- |
| 1      | Принимать запросы нового и существующих партнёров по OpenRTB, возвращать ставку или корректный отказ от участия |
| 2      | Подбирать рекламу по условиям кампании, сравнивать ставки и определять победителя                               |
| 3      | Управлять кампаниями, рекламными материалами, ставками и бюджетами через кабинет                                |
| 4      | Выдавать рекламные материалы пользователям сайтов и приложений                                                  |
| 5      | Принимать показы, клики и уведомления партнёров, необходимые для учёта и оплаты                                 |
| 6      | Пополнять бюджеты через платёжный шлюз, вести списания и счета без повторного начисления                        |
| 7      | Строить отчёты по кампаниям и расходам                                                                          |
| 8      | Подключать несколько площадок через отдельные адаптеры, сохраняя общую логику аукциона                          |

№ 1-7 обязательны для первого этапа с сохранением существующих функций. Расширение набора интеграций по требованию № 8 относится к итоговому решению.

## 3. Атрибуты качества

Для справки: P - приоритет

P0 означает обязательное условие запуска партнёра. 
P1 означает требование к безопасной эксплуатации и дальнейшему развитию. 


| Атрибут                      | Приоритет и срок          | Проверка                                                                                                                      |
| ---------------------------- | ------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| Время ответа                 | P0, 3 месяца              | При 18 000 запросов/с общий P95 не более 100 мс. Для нового партнёра ответ не более 80 мс по согласованному способу измерения |
| Производительность           | P0, 3 месяца; рост за год | Не менее 18 000 запросов/с на первом этапе и 50 000 через год, включая длительную нагрузку и всплески                         |
| Корректность финансов        | P0, оба этапа             | Повтор события не вызывает повторного списания. Параллельные ставки не превышают выделенный бюджет                            |
| Сохранность событий          | P0, оба этапа             | Подтверждённые события восстанавливаются после предусмотренных отказов, повторная обработка безопасна                         |
| Изоляция нагрузки            | P0, 3 месяца              | Построение отчётов или сбой кабинета не останавливает расчёт ставок                                                           |
| Доступность                  | P1, год                   | Не менее 99,9% за согласованный период. проверено переключение на резерв и восстановление                                     |
| Масштабируемость             | P1, оба этапа             | Число экземпляров сервиса ставок и обработчиков событий увеличивается независимо                                              |
| Сопровождение                | P1, с первого этапа       | Есть метрики времени ответа, ошибок, очередей и баз. Автоматизированы выпуск версий и откат                                   |
| Безопасность                 | P1, оба этапа             | Защищённые соединения, разграничение доступа рекламодателей, отдельные права сервисов и журнал финансовых операций            |
| Работа в нескольких регионах | P1, год                   | При отказе региона запросы перенаправляются без повторного расходования одного бюджета                                        |
| Стоимость и понятность       | P1, оба этапа             | Каждому сервису назначен ответственный, затраты на инфраструктуру и сопровождение укладываются в согласованный бюджет         |

P95 означает, что 95% запросов укладываются в указанное время. Ограничение партнёра в 80 мс нельзя автоматически считать P95: в ТЗ оно задано как стабильное время ответа. 

## 4. Ограничения

**Бизнес:** три месяца до подключения, ограниченный бюджет, запрет полной переработки и необходимость сохранять работу клиентов. В компании 35 человек всего, включая поддержку и менеджмент. Отдельных специалистов по надёжности, техническому документированию и бизнес-анализу нет.

**IT:** существующий стек C++ / Go / Python / Node.js и PostgreSQL, один рабочий кластер, нет кеша, брокера сообщений и контейнеризации, развёртывание ручное. Новые инструменты нужно вводить постепенно, с учётом навыков команды.

**Данные:** денежные операции требуют транзакций и идемпотентности. Отчёты могут обновляться с задержкой, но допустимое время нужно согласовать. Разделение сервисов должно сопровождаться разделением ответственности за данные.
