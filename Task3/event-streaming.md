# Потоковая обработка событий

## 1. Общая схема

Сборщик принимает показы, клики и уведомления партнёров и публикует их в Kafka. Сервис учёта проверяет повторы и создаёт команды списания. Аналитика независимо строит отчёты. Изменения кампаний и лимитов идут через тот же брокер отдельными топиками в сервис обновления кеша.

Приём события подтверждается только после записи Kafka. Доставка может повторяться, поэтому обработчики обязаны проверять идентификаторы.

## 2. Топики и хранение

Топик является отдельным потоком сообщений. Внутри него сообщения распределяются по разделам по указанному ключу.

| Топик | Содержание | Ключ раздела | Политика хранения |
|---|---|---|---|
| `ad.events.v1` | Показы, клики, победы и уведомления об оплате | `bid_id` | Удаление через 7 дней; дополнительный архив 30 дней |
| `campaign.changes.v1` | Полное актуальное состояние кампании с версией | `campaign_id` | Уплотнение: сохраняется последнее состояние каждого ключа |
| `budget.grants.v1` | Выдача и изменение лимитов | `grant_id` | 7 дней; действительные лимиты восстанавливаются также из финансовой БД |
| `billing.commands.v1` | Команды списания с постоянным идентификатором | `account_id` | 30 дней |
| `processing.errors.v1` | Некорректные сообщения и причина ошибки | Исходный `event_id` | 30 дней для разбора и исправления |

В топике кампаний удаление передаётся записью с пустым значением по ключу. Такие отметки сохраняются не менее 7 дней. После более долгой остановки получатель загружает полный снимок, чтобы не вернуть удалённые кампании. Последнее состояние в уплотняемом топике не является историей всех изменений. [Политики хранения Kafka](https://kafka.apache.org/41/configuration/topic-configs/).

Число разделов выбирается по частоте и размеру событий, а не по числу запросов ставок. Порядок есть только внутри одного раздела; версии кампаний и проверка повторов обязательны даже при таком порядке.

## 3. Формат события

Выбран **JSON**: он уже используется во внешнем API, понятен при разборе ошибок и не требует отдельного двоичного формата на первом этапе. Схема фиксируется через JSON Schema и проверяется сборщиком. Avro имеет смысл рассмотреть при подтверждённой необходимости сократить размер потока.

Пример события показа:

```json
{
  "event_id": "evt-1042",
  "schema_version": 1,
  "event_type": "impression",
  "event_time": "2026-10-15T12:00:00Z",
  "partner_id": "dsp-1",
  "request_id": "req-501",
  "bid_id": "bid-501-1",
  "campaign_id": "campaign-12",
  "account_id": "account-7"
}
```

Для уведомления об оплате дополнительно обязательны `grant_id`, сумма в целых долях валюты и код валюты. Для изменений кампаний передаются версия и полное состояние, для лимитов также владелец и срок действия. Идентификаторы счёта и кампании проверяются по доверенным данным, а не принимаются из произвольного браузерного запроса.

Новые необязательные поля допускаются в текущей версии. Несовместимое изменение требует новой версии схемы и согласованного перехода получателей. Полные пользовательские данные не включаются без необходимости.

## 4. Группы получателей

| Группа | Что читает | Результат |
|---|---|---|
| `event-accounting` | `ad.events.v1` | Проверка оплачиваемых событий, запись учёта и будущих команд в PostgreSQL |
| `analytics` | `ad.events.v1` | Загрузка событий и построение отчётов в ClickHouse |
| `snapshot-projector` | `campaign.changes.v1`, `budget.grants.v1` | Обновление Redis |
| `billing` | `billing.commands.v1` | Идемпотентные операции в финансовой PostgreSQL |
| `event-archive` | `ad.events.v1` | Архив в объектном хранилище |

У каждой группы своя позиция чтения. Остановка аналитики не останавливает учёт событий. Число одновременно работающих получателей одной группы не превышает число разделов её потока.

Получатель подтверждает обработку после сохранения результата. Временная ошибка вызывает повтор с растущей задержкой. Некорректное сообщение переносится в поток ошибок с уведомлением ответственного; исходная позиция подтверждается только после сохранения этого сообщения. Для финансовых сообщений разбор обязателен, пропуск без следа запрещён.

Ключи финансовой идемпотентности хранятся вместе с операциями. Учёт повторов событий должен покрывать окно повторной обработки и опоздания; для предложенного архива это не менее 30 дней плюс согласованный срок опоздания. В ClickHouse отчёты строятся по уникальным `event_id`, чтобы повторная загрузка не удваивала показатели. На одно лишь фоновое объединение строк полагаться нельзя.

## 5. Сохранность потока

Для Kafka задаются три копии каждого раздела в разных зонах, `acks=all`, `min.insync.replicas=2` и идемпотентная публикация. Выбор заведомо отставшей копии ведущей запрещён. При нехватке доступных копий запись не подтверждается, отправитель повторяет её с прежним идентификатором.

Изменение кампании, лимита или команды списания публикуется из таблицы исходящих сообщений в базе владельца. Запись данных и будущего сообщения выполняется одной транзакцией. Это не позволяет потерять сообщение между изменением базы и отправкой в Kafka.

Для другого региона поддерживается асинхронная копия потока. Kafka не заменяет резервные копии и не гарантирует однократное финансовое действие. Проверяются отставание групп, свободное место, ошибки публикации и срок до удаления непрочитанных сообщений. Правила архивирования и восстановления приведены в [database-strategy.md](database-strategy.md).
