# Стратегия хранения данных

## 1. База для каждого сервиса

| Сервис | Тип базы или хранилища | Данные и обоснование |
|---|---|---|
| Сервис ставок | Память процесса и Redis, без постоянной БД | Подготовленные кампании, правила ставок и выделенные лимиты. Локальное чтение не добавляет сетевую задержку в расчёт |
| Сервис кампаний | PostgreSQL и объектное хранилище | Кампании и связи между ними требуют транзакций и SQL. Файлы рекламы удобнее хранить отдельно от таблиц |
| Сервис статистики | Kafka для потока; PostgreSQL для учёта оплачиваемых событий | Kafka принимает большой поток показов и кликов. PostgreSQL хранит признаки обработанных финансово значимых событий и команды списания, защищая от повторов |
| Сервис аналитики | ClickHouse | Столбцовое хранение подходит для отчётов и суммирования большого числа событий, не нагружает основные базы |
| Сервис финансов | PostgreSQL | Балансы, платежи, резервы и списания требуют транзакций, точных денежных значений и уникальных ключей операций |

В предыдущих заданиях статистика разделена на сборщик и сервис учёта событий. Сборщик не имеет своей постоянной БД, а PostgreSQL принадлежит сервису учёта. Все сырые показы и клики в неё не копируются. Долговременные события и отчёты принадлежат аналитике.

Каждый сервис обращается только к своей основной базе. Другие сервисы получают данные через API или события. Исключение, заданное ранее: сервис выдачи может читать рекламные файлы, записанные сервисом кампаний. Redis не является источником денежного баланса.

На переходном этапе допустимы отдельные базы и пользователи на одном сервере PostgreSQL. Это разделяет права, но не защищает от общего отказа. В целевом решении критичные базы имеют отдельные ресурсы и резервные узлы.

## 2. Цели восстановления

**RPO** показывает, за какой последний период допускается потеря данных. **RTO** показывает, за какое время должна восстановиться работа. Значения являются целями, которые проверяются испытанием.

| Сервис | RPO при отказе одного узла или зоны | RTO при таком отказе | При полной потере региона: RPO / RTO |
|---|---|---|---|
| Ставки | Основные данные не теряются; локальные копии загружаются заново | До 30 секунд за счёт работающих экземпляров | Наследует сохранность кампаний и финансов / до 5 минут для кампаний с безопасными лимитами |
| Кампании | 0 для подтверждённых изменений | До 1 минуты | До 5 минут / до 30 минут |
| Статистика | 0 для принятых в Kafka событий и подтверждённого учёта | До 1 минуты | До 5 минут / до 30 минут |
| Аналитика | 0 при сохранности Kafka и архива; допустимо отставание отчётов | До 5 минут | До 5 минут исходных событий / до 4 часов с повторной обработкой |
| Финансы | 0 для подтверждённых транзакций | До 1 минуты | До 5 минут / до 1 часа со сверкой перед возобновлением операций |

Нулевой RPO PostgreSQL в пределах региона требует синхронного подтверждения резервным узлом в другой зоне. Если такой узел недоступен, запись приостанавливается, а не переключается незаметно на менее надёжный режим. Kafka должна сохранять подтверждённые события на нескольких узлах. [Репликация PostgreSQL](https://www.postgresql.org/docs/current/warm-standby.html).

Между регионами выбрана асинхронная передача ради стоимости и задержек. Поэтому нулевой RPO при потере всего региона не обещается. Цель до 5 минут требует контроля отставания PostgreSQL, Kafka и архива событий; если канал отстаёт больше, цель уже не выполняется.

После восстановления финансов из отстающей копии нельзя считать отсутствующие резервы свободными деньгами. Новые лимиты и списания приостанавливаются до сверки с сохранёнными событиями и данными партнёров. Если сверка не завершилась за час, RTO нарушен, но небезопасная выдача денег не разрешается. Полное восстановление ставок также зависит от этой проверки.

## 3. Резервное копирование

| Хранилище | Стратегия |
|---|---|
| PostgreSQL кампаний, учёта и финансов | Полная копия раз в сутки, непрерывная передача журнала WAL, хранение 30 дней. Копии и журналы находятся также в другом регионе |
| Kafka | Репликация внутри региона и асинхронная копия потока в другом. Сырые события дополнительно архивируются в объектное хранилище не реже раза в 5 минут, хранятся 30 дней |
| ClickHouse | Ежедневная копия таблиц и схем, хранение 30 дней. Изменения после копии восстанавливаются из Kafka или архива событий |
| Redis | Не является единственным источником данных. Восстанавливается из баз владельцев и потока обновлений |
| Рекламные файлы | Версии объектов и копия в другом регионе; удалённые версии сохраняются 30 дней |

WAL позволяет восстановить PostgreSQL на момент перед ошибочным изменением, а не только на дату суточной копии. Репликация не заменяет резервную копию: ошибочное удаление попадёт и на резервный узел. Основа: [восстановление PostgreSQL на момент времени](https://www.postgresql.org/docs/current/continuous-archiving.html).

Для восстановления аналитики вместе с копией сохраняется позиция обработки событий. Повторная загрузка не должна удваивать показатели. Данные архива удаляются только после проверки, что доступна пригодная копия, покрывающая начало оставшегося журнала. Срок хранения дедупликации должен покрывать разрешённое окно повторной обработки.

Раз в месяц проверяется восстановление в отдельной среде: запуск баз, полнота событий и сверка финансов. Время и возможная потеря сравниваются с таблицей RPO/RTO.

## 4. Принципы 12-факторных приложений

| Принцип | Применение в AdScale |
|---|---|
| Кодовая база | Код сервиса и миграции его БД хранятся под контролем версий |
| Зависимости | Версии библиотек и клиентов хранилищ заданы явно |
| Конфигурация | Адреса баз и настройки передаются через окружение; секреты не записываются в код |
| Внешние ресурсы | PostgreSQL, Redis и Kafka подключаются по конфигурации, без жёсткой привязки к серверу |
| Сборка, выпуск, запуск | Сборка отделена от настроек окружения; миграции выполняются управляемо при выпуске |
| Процессы | Постоянное состояние хранится вне процессов. Память ставок содержит временные копии; потерянные резервы удерживаются у финансового сервиса |
| Привязка портов | API сервиса доступен через собственный сетевой порт |
| Параллельность | API и обработчики событий масштабируются отдельными процессами |
| Быстрый запуск и остановка | После прогрева сервис принимает запросы; при остановке завершает работу и не подтверждает несохранённые события |
| Сходство сред | В тестовой и рабочей среде используются одинаковые типы хранилищ и совместимые версии |
| Журналы | Приложения пишут журналы в стандартный вывод, сбор и хранение выполняются отдельно |
| Административные задачи | Миграции, сверки и восстановление выполняются отдельными командами того же выпуска |
