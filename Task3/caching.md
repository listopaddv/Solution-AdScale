# Кеширование

## 1. Что хранится в кеше

| Данные | Где находятся | Предлагаемый срок действия |
|---|---|---|
| Активные кампании, условия подбора и рекламные материалы | Redis и память сервиса ставок | До 30 секунд с момента подтверждения актуальности владельцем |
| Настроенные ставки и правила расчёта | В составе копии кампании | Тот же срок, до 30 секунд |
| Выделенные бюджетные лимиты | Redis для доставки; память назначенного обработчика для использования | До 5 секунд на выдачу новых ставок, но не дольше срока лимита от финансового сервиса |
| Готовый ответ на аукцион | Не кешируется для других запросов | Не применяется |

TTL ограничивает время использования копии. Он не заменяет обновления по событиям. Значения выбраны как начальные: кампании меняются реже запросов ставок, а денежные лимиты требуют более короткого срока.

Общий баланс не используется как разрешение на расход. Финансовый сервис заранее резервирует отдельную сумму за обработчиком. Используется остаток именно этого лимита.

## 2. Размещение Redis

Redis располагается в частной сети каждого региона рядом с сервисами ставок. На первом этапе достаточно основного узла и резервного в другой зоне с автоматическим переключением. При нехватке мощности применяется Redis Cluster с резервной копией каждого шарда.

Сервис ставок читает Redis только в фоне. При расчёте он обращается к памяти процесса. Поэтому задержка Redis не добавляется к времени ответа партнёру.

Репликация Redis асинхронная и может потерять последние обновления при переключении. Это приемлемо для восстанавливаемого кеша, но не для единственного хранилища денег. Источник лимитов остаётся в финансовой PostgreSQL. [Репликация Redis](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/).

## 3. Обновление и инвалидация

1. Сервис кампаний или финансов сохраняет изменение и сообщение для публикации одной транзакцией.
2. Сообщение проходит через Kafka в сервис обновления кеша.
3. Новая версия заменяет запись Redis, затем локальную копию в сервисе ставок.
4. Событие остановки или удаления кампании запрещает её использование. Старая версия не должна восстановить удалённую запись.

Каждая копия содержит версию и абсолютный срок действия `valid_until`. Повторная доставка или чтение старого Redis не продлевают этот срок. Продление допускается только после подтверждения актуальности у владельца данных.

При исправном потоке остановка кампании применяется сразу после получения события. При потере связи допускается использование прежней копии не дольше её срока, максимум 30 секунд. Это ограничение нужно согласовать; если требуется более быстрая остановка, срок действия сокращается.

Повторное обновление лимита с тем же `grant_id` не сбрасывает уже израсходованный остаток. Истечение TTL запрещает новые ставки, но не освобождает резервы по старым предложениям. После перезапуска процесс получает новый лимит, а неизвестный остаток старого остаётся у финансового сервиса до сверки.

## 4. Прогрев кеша

При запуске загружается согласованный снимок активных кампаний и позиция потока обновлений. Затем применяются более новые события, проверяются версии и сроки действия. Только после этого экземпляр включается в балансировку.

Redis восстанавливается тем же способом из данных владельцев, если его копия потеряна. Новый экземпляр ставок заранее загружает нужные кампании из Redis, но не продолжает расходовать лимит другого процесса. Сначала ему выдаётся собственный лимит.

## 5. Работа при сбоях

При временной недоступности Redis сервис использует действительные локальные копии. После истечения срока кампании или лимита возвращается отказ от участия. Синхронный запрос в PostgreSQL вместо кеша не выполняется, иначе перегрузка снова попадёт в обработку ставки.

Контролируются возраст данных, задержка обновлений и число отказов из-за отсутствующих копий. Полная очистка кеша без прогрева не применяется при обычном выпуске версии.
