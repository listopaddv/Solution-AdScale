# Масштабирование хранилищ

## 1. Репликация

Для PostgreSQL применяется схема основной узел + резервный узел, указанная в задании как master-slave. Запись идёт в основной узел. Синхронный резерв расположен в другой зоне того же региона и используется при отказе. Перед переключением старый основной узел должен потерять право записи, чтобы не возникло двух независимых владельцев данных.

В целевом решении для PostgreSQL заранее готовится второй резерв в третьей зоне. Запись подтверждает хотя бы один актуальный резерв. Это позволяет после отказа основного узла сохранить синхронное подтверждение и не ждать создания новой копии.

| Сервис | Репликация и чтение |
|---|---|
| Кампании | Основной PostgreSQL и синхронный резерв. При росте чтений добавляется асинхронная копия для списков и просмотра кампаний |
| Финансы | Основной PostgreSQL и синхронный резерв. Баланс, резервы и списания читаются и изменяются на основном узле, без отстающих копий |
| Статистика | PostgreSQL учёта с синхронным резервом; Kafka с тремя копиями раздела в разных зонах |
| Аналитика | ClickHouse с двумя копиями каждого шарда в разных зонах. Запросы отчётов распределяются между доступными копиями |
| Ставки | Несколько экземпляров приложения с собственными данными в памяти; Redis с резервным узлом |

Для аналитики не нужна копия финансовой или общей PostgreSQL: отчёты уже вынесены в ClickHouse. Временная PostgreSQL-копия для отчётов допустима только на переходном этапе. В целевом решении чтения масштабируются копиями ClickHouse; его репликация не требует единственного постоянного ведущего узла для таблицы. [Репликация ClickHouse](https://clickhouse.com/docs/reference/engines/table-engines/mergetree-family/replication).

Копия для чтения может отставать. Сразу после изменения кампании подтверждённые данные читаются у владельца, а не с отстающего узла.

## 2. Шардирование

Шардирование разделяет данные между несколькими узлами и увеличивает доступный объём записи. Репликация хранит копии одних данных и защищает от отказа. Эти механизмы дополняют друг друга.

| Данные | Ключ разделения | Когда и почему |
|---|---|---|
| Кампании PostgreSQL | `advertiser_id` | При нехватке мощности одного сервера; кампании рекламодателя остаются вместе |
| Финансы PostgreSQL | `account_id` | Только после измерений. Операции, лимиты и ключи идемпотентности одного счёта находятся в одном шарде |
| Учёт оплачиваемых событий PostgreSQL | `account_id` | При росте записи; повторная команда попадает в тот же шард, что и исходная |
| События ClickHouse | Хеш `bid_id` | Распределяет массовые события, включая крупные кампании. Отчёт по кампании собирается с нескольких шардов |
| Redis | Хеш ключа кампании или лимита | Redis Cluster вводится при нехватке памяти или мощности одного основного узла |

Внутри ClickHouse события дополнительно разбиваются по месяцу события. Это облегчает удаление старых данных, но не заменяет распределение по серверам. Для регулярных отчётов хранятся дневные итоги по кампаниям.

PostgreSQL сам по себе не распределяет таблицу по независимым серверам: при введении шардов маршрутизацию по ключу выполняет слой доступа сервиса. Межшардовые денежные операции на первом этапе не вводятся. Очень крупный счёт может остаться отдельным ограничением и потребовать выделенного шарда.

## 3. CQRS

CQRS означает разделение моделей записи и чтения. В AdScale оно применяется в двух местах:

- **Кампании и ставки:** изменения сохраняются в PostgreSQL, а для быстрого расчёта готовятся отдельные представления в Redis и памяти. Они обновляются через события и могут кратковременно отставать.
- **События и аналитика:** поток принимается через Kafka, для отчётов строятся таблицы и итоги в ClickHouse.

Денежный баланс не рассчитывается по отстающему отчёту. Финансовый сервис остаётся единственным владельцем подтверждённых денежных операций.

## 4. Этапы и регионы

В первые три месяца нужны разделение нагрузки, резервные узлы PostgreSQL, Kafka, Redis и изоляция аналитики. Для перехода к 50 000 запросов/с сначала добавляются экземпляры ставок и обработчики событий, затем шарды хранилищ при необходимости.

Нельзя приравнивать 50 000 запросов ставок/с к 50 000 записей в каждую БД. Мощность оценивается отдельно по частоте событий, денежным операциям, размеру сообщений и времени выполнения отчётов.

Через год в каждом регионе размещаются сервисы ставок и свой Redis. У финансового счёта один регион-владелец записи. Другие регионы получают непересекающиеся лимиты. При отказе региона новые лимиты выдаются только после безопасной смены владельца и сверки; старые лимиты не используются повторно. Цели восстановления определены в [database-strategy.md](database-strategy.md).
