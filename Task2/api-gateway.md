# Шлюз для DSP-интеграции

## 1. Необходимость API Gateway

Он создаёт единый контролируемый вход для партнёра: проверяет доступ, ограничивает поток, выбирает сервис и измеряет время ответа. Для ставок используется отдельный шлюз RTB, а кабинет продолжает работать через шлюз управления из задания 1. Отчёты и административные операции не занимают ресурсы входа RTB.

Выбор: **Envoy и небольшой адаптер на Go**. Envoy отвечает за HTTPS, маршрутизацию и защиту соединений. Адаптер проверяет OpenRTB, учитывает особенности площадки, вызывает сервис ставок по gRPC и переводит результат обратно в OpenRTB.

Envoy выбран из-за поддержки HTTP/2, gRPC, ограничений нагрузки и метрик. Это позволяет использовать готовые сетевые механизмы и оставить в адаптере только логику интеграции.

## 2. Маршрутизация и доступ

| Маршрут | Получатель |
|---|---|
| `POST /openrtb2/auction` | Адаптер -> сервис ставок |
| Уведомления о победе и оплате | Сборщик событий в отдельном пуле ресурсов |
| Показы и клики из рекламы | Сборщик событий |
| Кампании, бюджеты и отчёты | Отдельный шлюз управления |

Для DSP предлагается mTLS: обе стороны проверяют сертификаты. Сертификат сопоставляется с зарегистрированным партнёром, а заявленный в запросе идентификатор не считается доказательством доступа. Список разрешённых партнёров хранится локально и обновляется в фоне, без обращения к службе авторизации на каждый аукцион.

Между шлюзом и сервисом ставок также используется mTLS. Браузерные события проверяются отдельно по подписанным ссылкам, поскольку браузер не имеет сертификата DSP. Размер тела, формат и версия OpenRTB ограничиваются согласованным профилем.

Адаптеры и обработчики разворачиваются в нескольких экземплярах. Балансировка направляет запросы только в готовые экземпляры. Повторная отправка уже начатого расчёта на другой узел отключена.

## 3. Ограничение нагрузки

Для каждого партнёра задаётся допустимое число запросов в секунду и небольшой запас на краткий всплеск. Также ограничиваются одновременные запросы и длина очереди. При перегрузке запрос быстро отклоняется, а не ждёт до тайм-аута.

Для первого этапа используются локальные ограничения Envoy. Общий лимит партнёра делится между экземплярами шлюза; при изменении их числа доли пересчитываются. Каждый экземпляр не должен получать полный общий лимит. Такой вариант может неравномерно использовать мощность, зато не требует синхронного Redis на каждом запросе. Механизм описан в [документации Envoy](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/local_rate_limit_filter).

18 000 запросов/с из кейса относятся ко всей системе, а не к квоте только нового партнёра. Конкретные доли и запас определяются нагрузочным испытанием и договором.

## 4. Распределение времени

Предварительный расчёт для требования 80 мс:

| Этап | Предлагаемый предел |
|---|---|
| Внешняя сеть до AdScale и обратно | 20 мс |
| Шлюз и проверка запроса | 10 мс |
| gRPC, ожидание исполнения и расчёт ставки | 35 мс |
| Формирование и отправка ответа | 5 мс |
| Резерв времени | 10 мс |
| **Всего** | **80 мс** |

Таким образом, на стороне AdScale закладывается до 60 мс. Это предложение для проверки, а не измеренная гарантия. Если сеть занимает больше 20 мс, потребуется размещение ближе к партнёру или пересмотр внутреннего распределения.

Для каждого запроса выбирается меньший предел из 80 мс и `tmax` из OpenRTB. Из него вычитаются сетевой резерв и уже прошедшее время. Если времени на расчёт и ответ уже недостаточно, расчёт не начинается. Все внутренние ограничения должны укладываться в общий срок, а не складываться поверх него.

Срок отсчитывается с начала приёма запроса. 

## 5. Автоматический размыкатель

Circuit Breaker прекращает вызовы, которые постоянно отвечают ошибками, и периодически проверяет их восстановление.

| Состояние | Поведение адаптера |
|---|---|
| Закрыт | Запросы идут в сервис ставок, ошибки учитываются |
| Открыт | Новые вызовы временно прекращаются, возвращается быстрый технический отказ |
| Проверка восстановления | Пропускается небольшое число запросов; успех возвращает обычную работу, ошибка снова открывает размыкатель |

Начальный пример настройки: пять последовательных технических ошибок открывают размыкатель на пять секунд. Затем допускается один проверочный вызов. Параметры уточняются на испытаниях. Отсутствие подходящей рекламы или бюджета не считается поломкой сервиса.

Размыкатель реализуется в gRPC-клиенте адаптера. Дополнительно Envoy ограничивает число активных соединений и запросов, а неработающие экземпляры исключаются из балансировки.

Для фоновых обращений к Redis применяется такой же принцип: временная пауза после серии ошибок, потом проверка восстановления. Пока зависимости недоступны, разрешены только действительные локальные данные и лимиты. Правила повторов и финансовой идемпотентности приведены в [interaction.md](interaction.md).

## 6. Мониторинг и проверка

Собирать по каждому партнёру:

- число запросов, P95 и P99 полного времени ответа;
- время шлюза и gRPC-вызова, ожидание в очереди;
- технические ошибки, тайм-ауты и отказы из-за перегрузки;
- долю ставок и отказов от участия с причинами;
- состояние размыкателя, возраст данных, отставание обработчиков событий.

Использовать общий идентификатор запроса в журналах и выборочных трассировках. Не записывать полные пользовательские данные в обычный журнал.

Перед запуском проверить 18 000 запросов/с, короткие всплески, отказ Redis, остановку экземпляра сервиса ставок, недоступность Kafka и повторное событие оплаты. Ожидается соблюдение времени ответа, отсутствие двойных списаний и восстановление подтверждённых событий. Проверять нужно весь путь до партнёра, а не только время gRPC.

Общий P95 до 100 мс и требование партнёра до 80 мс учитываются отдельно. Рост доли отказов не должен скрывать перегрузку. Нельзя считать SLA выполненным только потому, что система быстро отклоняет все запросы.
