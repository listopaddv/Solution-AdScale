# Сервис ставок

## 1. Границы и ответственность

Из монолита выделяется отдельный сервис на C++, который объединяет подбор рекламных кандидатов и расчёт ставки. Это позволяет сохранить существующую логику аукциона и масштабировать её независимо от кабинета и аналитики.

Сервис выполняет четыре действия:

1. Получает проверенный запрос от шлюза RTB.
2. Подбирает кампании и материалы по условиям показа.
3. Проверяет выделенный бюджет и рассчитывает предложение.
4. Возвращает ставку или отказ от участия.

Итоговую победу на своей площадке определяет партнёр. Сервис AdScale выбирает предложение, которое отправляется ему.

Сервис ставок не изменяет кампании, не проводит платежи, не списывает деньги окончательно и не строит отчёты.

## 2. API

Внешний OpenRTB-запрос принимает шлюз. Между шлюзом и сервисом ставок используется один метод gRPC:

```text
BiddingService.Bid(BidRequest) -> BidResult
```

| Сообщение           | Основные поля                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `BidRequest`        | Идентификаторы запроса, партнёра и показов. Сайт или приложение. Параметры устройства. Формат рекламы. Минимальная цена Валюта |
| `BidResult`: ставка | Идентификаторы запроса, показа, ставки, кампании и материала. Цена. Готовая разметка или ссылка на материал                    |
| `BidResult`: отказ  | Причина: нет подходящей рекламы, нет бюджета, устарели данные или недостаточно времени                                         |

Шлюз устанавливает срок завершения gRPC-вызова по оставшемуся времени запроса. Сервис прекращает работу при отмене. Отказ от участия является обычным результатом, а недоступность сервиса и превышение времени возвращаются как технические ошибки. 

Для эксплуатации предусмотрены проверка работоспособности, проверка готовности к запросам и выдача метрик. Новый экземпляр получает трафик только после загрузки данных.

## 3. Зависимости

| Зависимость | Назначение | Участие в расчёте одной ставки |
|---|---|---|
| Шлюз RTB | Передаёт запрос и получает результат | Синхронно |
| Локальная память | Кампании, материалы и выделенные лимиты | Чтение и проверка во время расчёта |
| Redis | Подготовленные копии данных | Только фоновое обновление |
| Сервис кампаний | Источник условий кампаний | Изменения через Kafka и сервис обновления кеша |
| Финансовый сервис | Выделяет ограниченный бюджет | Обновления через Kafka и сервис обновления кеша |
| Сборщик событий | Принимает показы, клики и уведомления | Отдельный поток после ответа |

На пути ставки нет запросов к PostgreSQL, сервису кампаний, платёжному шлюзу или аналитике. Сервис также не ждёт записи события в Kafka.

## 4. Модель данных

Собственная постоянная БД сервису ставок не нужна. Основные данные хранятся у владельцев, а подготовленные копии поступают в память через Redis.

| Объект | Основные поля | Источник |
|---|---|---|
| Кампания | `campaign_id`, статус, условия подбора, ставка, валюта, версия, срок актуальности | Сервис кампаний |
| Рекламный материал | `creative_id`, `campaign_id`, формат, размеры, разметка или ссылка, статус проверки | Сервис кампаний |
| Выделенный лимит | `grant_id`, `campaign_id`, владелец, сумма, остаток, валюта, срок действия | Финансовый сервис |
| Резерв ставки | `bid_id`, `grant_id`, максимальная сумма оплаты, время создания | Сервис ставок |

В памяти создаются индексы по параметрам подбора рекламы. Новая версия данных сначала проверяется, затем целиком заменяет старую. Повторное или запоздавшее обновление не должно сбрасывать использованный лимит.

Денежные значения хранятся целыми долями валюты. Цена OpenRTB задаётся за тысячу показов (CPM), а резерв бюджета рассчитывается на конкретный показ. Например, 1 USD CPM соответствует 0,001 USD за один показ.

Финансовый сервис заранее резервирует сумму за конкретным обработчиком. Проверка и уменьшение локального остатка выполняются атомарно, чтобы параллельные запросы не потратили один лимит дважды. После перезапуска старый лимит не используется заново: неизвестный остаток удерживается до сверки. Истечение срока лимита запрещает новые ставки, но само по себе не освобождает деньги по уже выданным предложениям.

## 5. Резервные стратегии

| Ситуация | Решение |
|---|---|
| Redis временно недоступен | Использовать последнюю локальную копию, пока она действительна |
| Данные кампании или лимит устарели | Отказаться от участия |
| Бюджет закончился | Отказаться от участия |
| Расчёт не успевает завершиться | Прекратить работу, не запускать повторный расчёт |
| Нет подходящей кампании | Вернуть обычный отказ от участия |

Кешируются данные и правила, а не готовые ответы на чужие аукционы. Произвольная ставка по умолчанию не используется: она может нарушить условия кампании или бюджет. Более простая резервная ставка допустима только как заранее настроенное правило кампании с теми же проверками бюджета.

## 6. Выделение из монолита

Сначала вынести интерфейс расчёта и подготовить обновление кампаний и лимитов. Затем сравнить старый и новый алгоритмы на одинаковых запросах без двойного участия в реальном аукционе. После проверки постепенно переключать трафик.

Кампании и финансы могут временно оставаться модулями монолита, но должны предоставлять новому сервису те же данные и ограничения. При откате нельзя заново выдавать средства, уже зарезервированные новым сервисом.
