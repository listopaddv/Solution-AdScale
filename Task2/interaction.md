# Взаимодействие сервисов

## 1. Выбор протоколов

| Взаимодействие | Решение | Обоснование |
|---|---|---|
| DSP -> шлюз RTB | HTTPS, OpenRTB 2.6, JSON | Стандартный формат обмена рекламными запросами |
| Шлюз RTB -> сервис ставок | gRPC, Protobuf | Компактный формат, строгий контракт, поддержка срока завершения; подходит для частых внутренних вызовов |
| Кабинет -> сервис кампаний | REST, JSON через шлюз управления | Простые операции над кампаниями, удобство отладки и интеграции с интерфейсом |
| Сервис кампаний -> сервис ставок | Асинхронные изменения через Kafka, Redis и локальную память | Расчёт ставки не ждёт ответ сервиса кампаний |
| Показы, клики и уведомления | HTTPS -> сборщик -> Kafka | Приём отделён от обработки, всплески сглаживаются, события можно обработать повторно |

REST для сервиса ставок тоже возможен, но для выбранного внутреннего взаимодействия предпочтён gRPC. Это не обещание автоматически меньшей задержки: результат нужно проверить нагрузкой. Kafka не используется для запроса и ответа на ставку, поскольку ожидание очереди затрудняет соблюдение 80 мс.

API кампаний включает `POST /v1/campaigns`, `GET /v1/campaigns/{id}` и `PATCH /v1/campaigns/{id}`. Изменения проверяются на доступ рекламодателя и версию записи. gRPC для этих операций не требуется: они не входят в обработку аукциона.

## 2. Внешний API для DSP

Сохраняем направление из кейса: партнёр отправляет запрос, AdScale возвращает предложение. Профиль OpenRTB и фактическую роль площадки нужно согласовать до подключения.

```text
POST /openrtb2/auction
Content-Type: application/json
x-openrtb-version: 2.6
```

| Часть | Основные поля |
|---|---|
| Запрос | `id`, `imp`, `site` или `app`, `device`, `tmax`, валюта |
| Предложение | `id`, `seatbid[].bid[]`: `id`, `impid`, `price`, `adm`, `crid` |
| Уведомления | Согласованные адреса `nurl` для победы и `burl` для оплаты; показы и клики поступают в сборщик событий |

Это основные поля, а не полное описание стандарта. `id` ответа соответствует запросу, `impid` указывает конкретный показ. `price` передаётся в CPM. Условия оплаты фиксируются отдельно: победа сама по себе не всегда означает списание.

| Ситуация | Ответ |
|---|---|
| Есть предложение | `200` и JSON OpenRTB |
| Нет подходящей ставки или действующего бюджета | `204` без тела |
| Некорректный запрос | `400` без тела |
| Нет прав доступа | Отклонение соединения при неверном сертификате либо `403` |
| Превышен разрешённый поток | `429` |
| Сервис недоступен | `503` |
| Истекло время ожидания сервиса | `504` |

Коды перегрузки и технических ошибок согласуются с партнёром. Если его профиль требует `204` в этих случаях, внутренняя метрика всё равно фиксирует технический отказ. Ошибки не должны исчезать из отчёта SLA.

Основа внешнего обмена: [OpenRTB 2.6](https://github.com/InteractiveAdvertisingBureau/openrtb2.x/blob/main/2.6.md). Конкретные поля и дополнительные ограничения проверяются по профилю нового партнёра.

## 3. Обновления и поток событий

**Кампании и лимиты:** владелец сохраняет изменение в своей PostgreSQL и запись для публикации одной транзакцией. Фоновый обработчик отправляет сообщение в Kafka. Сервис обновления кеша готовит новую версию в Redis, сервис ставок загружает её в память. Паттерн transactional outbox.

**Показы и клики:** сборщик проверяет событие, отправляет в Kafka и подтверждает приём только после подтверждения записи брокером. Сервис учёта событий удаляет повторы, сервис аналитики обновляет отчёты. Получатели работают независимо.

Минимальный состав события: `event_id`, `partner_id`, `request_id`, `bid_id`, `campaign_id`, тип, время и версия формата. Для события оплаты добавляются идентификатор резерва, сумма и валюта. Источник и право отправки уведомления проверяются до обработки.

Для Kafka предлагаются `acks=all`, включённая идемпотентная публикация и резервирование брокеров. Это не отменяет проверку повторов в приложении. При недоступности брокера сборщик не подтверждает приём; отправитель повторяет событие с тем же идентификатором.

Доставка из браузера может оборваться до приёма события. Поэтому обязательное основание списания должно поступать по согласованному надёжному каналу партнёра с повторами. Одного клика или показа из браузера недостаточно для обещания полной сохранности финансового учёта.

## 4. Повторные попытки

| Операция | Правило |
|---|---|
| Расчёт ставки | Не повторять после отправки в сервис: мало времени и неизвестно, был ли создан резерв |
| Фоновое чтение Redis или получение кампаний | Повторять с растущей задержкой и случайным разбросом |
| Публикация из таблицы исходящих сообщений | Сохранять сообщение до успешной отправки, повторять в фоне |
| Финансовая команда | Повторять только с прежним ключом идемпотентности |
| Ошибка формата или доступа | Не повторять автоматически, исправить причину |

Пример задержек для фоновых операций: 100, 200, 400, 800 мс, затем не более 5 секунд с небольшим случайным разбросом. После серии ошибок включается размыкатель и сигнал оператору. Сообщение при этом не удаляется. Ответственность за повторы назначается одному уровню, чтобы шлюз и клиент не умножали число попыток.

## 5. Идемпотентность финансовых операций

Сервис учёта событий проверяет не только `event_id`, но и бизнес-ключ, например `(partner_id, bid_id, тип оплаты)`. Это защищает от повторного уведомления с новым идентификатором.

Для каждого основания оплаты он создаёт одну команду списания с постоянным `billing_event_id`. Финансовый сервис в одной транзакции записывает этот ключ и проводит денежную операцию. Уникальность ключа запрещает второе списание. Повтор с другой суммой по тому же ключу направляется на разбор.

Команда содержит ссылку на резерв ставки. Сумма не превышает зарезервированный предел. Если обработчик упал или ответ потерялся, неизвестный резерв не выдаётся повторно до сверки. Поздние уведомления обрабатываются по согласованному сроку; окончание срока лимита на новые ставки не означает автоматического возврата всех денег.

Таким образом, Kafka допускает повторную доставку, но финансовое действие выполняется один раз. [Диаграмма событий](diagrams/events-sequence.svg) показывает порядок подтверждений.
